Del JSON a una tabla: así empieza Medallion

Las cifras de esta guía (tamaños, bytes, tiempos) son valores de referencia de ejecuciones reales del curso y pueden variar ligeramente en tu cuenta. Se ensayaron: la carga del método con 2,500 líneas reales, las estimaciones en seco y el patrón de envío de un lote Spark. No se ensayaron de principio a fin: la copia de war_tweets.txt con el cuaderno de Colab, la creación del bucket, la carga completa del archivo desde tu bucket y el script de Spark de este laboratorio.

Antes de empezar

  • Un proyecto de Google Cloud con facturación activa (de la sesión 1) y Cloud Shell abierto.
  • Cuenta de Google con acceso al archivo war_tweets.txt en Drive y al cuaderno de Colab del curso, que copia de Drive a Storage: https://colab.research.google.com/drive/1T3Q3HYP2j5n40EEj3QNX3iyDanKc99RZ.
  • Unos 22 GiB de almacenamiento disponibles en tu proyecto para el archivo y otros 22 GiB para la tabla Bronze.

Preparación, herramientas y ruta exacta

Ruta: Cloud Shell → crear el bucket → Colab para copiar el archivo → Cloud Shell para comprobarlo y cargarlo en BigQuery → BigQuery Studio para contar → Cloud Shell para estimar costos y enviar el lote de Spark. Sustituye TU_PROYECTO y TU_BUCKET por tus valores. El nombre del bucket debe ser único en todo el mundo.

Región y permisos: Usa la ubicación US para el bucket y para los datasets de BigQuery: la carga funciona cuando el bucket está en la misma ubicación o dentro de la multirregión del dataset. Para Dataproc Serverless usa una región de Estados Unidos (por ejemplo us-central1) y la misma en todos tus lotes.

Paso 1 · Copiar el archivo de Drive a tu bucket · 12 min

Dónde: Cloud Shell (ícono >_ arriba a la derecha de la consola de Google Cloud) para crear el bucket; después Google Colab, en otra pestaña, con el cuaderno del curso: https://colab.research.google.com/drive/1T3Q3HYP2j5n40EEj3QNX3iyDanKc99RZ.

Acción: Crea un bucket en la ubicación US (su nombre debe ser único en todo el mundo, por ejemplo tweets-TU_PROYECTO). Abre el cuaderno de Colab del curso (enlace arriba). Ejecuta sus dos primeras celdas: montar Drive y autenticarte con tu cuenta. En la celda que fija project_id y bucket_id escribe TU proyecto y TU bucket: el cuaderno trae valores de ensayo y, si los dejas, la copia falla por permisos. Agrega una celda con el comando de copia de war_tweets.txt (es el mismo patrón que usan las celdas de copia del cuaderno) y ejecútala: son 22 GiB y puede tardar un buen rato. Antes, el archivo debe aparecer en Mi unidad de tu Drive (si está en una carpeta compartida, agrégalo con clic derecho → Organizar → Añadir acceso directo). Cuando la celda termine, pasa al paso 2.

Costo estimado: Crear el bucket no cuesta. Guardar 22 GiB se cobra por GiB y por mes mientras el objeto exista; revisa los precios de tu clase de almacenamiento.

# Cloud Shell: crea tu bucket
gcloud config get-value project

Paso 2 · Comprobar el objeto y anotar su manifiesto · 8 min

Dónde: Cloud Shell.

Acción: Pide el tamaño y la huella del objeto. Si copiaste el archivo completo, el tamaño y la huella md5 coinciden con los valores de referencia: es la prueba de que tu copia es igual al original. Anota nombre, tamaño, huella y generación: es el manifiesto de tu Bronze.

Costo estimado: Pedir metadatos no tiene costo de consulta.

gcloud storage ls -l gs://TU_BUCKET/war_tweets.txt
gcloud storage objects describe gs://TU_BUCKET/war_tweets.txt \
  --format="yaml(name,size,storage_class,generation,md5_hash)"

Salida esperada:

TOTAL: 1 objects, 23663541134 bytes (22.04GiB)
---
md5_hash: nC490+y+7Rt3nDD02VE/pg==
name: war_tweets.txt

Comprueba: size es 23663541134 (22.04 GiB) y md5_hash es nC490+y+7Rt3nDD02VE/pg==. La generación y la clase de almacenamiento pueden ser distintas.

Error frecuente y recuperación: Si el tamaño es menor, la copia se interrumpió: repite el cuaderno de Colab. Si ls dice "One or more URLs matched no objects", revisa el nombre del bucket y del archivo.

Paso 3 · Crear tu Bronze en BigQuery · 12 min

Dónde: Cloud Shell.

Acción: Crea el dataset tweets_bronze en la ubicación US y carga el archivo completo en una sola columna llamada value. El truco: el archivo es JSON Lines (un JSON por línea); si indicas un separador de columnas que nunca aparece en el texto (þ) y desactivas las comillas (--quote=''), cada línea completa cae en value sin alterarse. --replace permite repetir el comando sin duplicar filas.

Costo estimado: La carga desde Cloud Storage no se factura como consulta. La tabla ocupará unos 22 GiB lógicos de almacenamiento en tu proyecto.

gcloud services enable bigquery.googleapis.com
bq --location=US mk --dataset tweets_bronze
bq --location=US load --replace --source_format=CSV \
  --field_delimiter='þ' --quote='' --max_bad_records=0 \
  tweets_bronze.entrada "gs://TU_BUCKET/war_tweets.txt" value:STRING

Salida esperada:

Dataset 'TU_PROYECTO:tweets_bronze' successfully created.
Waiting on bqjob_... (0s) Current status: RUNNING
...
Waiting on bqjob_... (Ns) Current status: DONE

Comprueba: bq show tweets_bronze.entrada muestra una sola columna (value, STRING) y 6,798,932 filas. El método se ensayó con 2,500 líneas reales: 2,500 filas y 2,500 ids distintos. La carga completa desde tu bucket no se midió.

Error frecuente y recuperación: "Not found: URI" indica un nombre de bucket o de archivo mal escrito. Si hay errores de registros malos, comprueba que escribiste --quote='' (dos comillas simples) y el delimitador þ tal cual (cópialo y pégalo).

Paso 4 · Contar filas y mirar un tweet crudo · 10 min

Dónde: BigQuery Studio → nueva consulta (con tu proyecto seleccionado) para contar; Cloud Shell para ver una línea sin costo.

Acción: Cuenta las filas (el estimador del editor debe decir 0 bytes). Después mira un tweet crudo de dos formas y compara su costo: leyendo los primeros bytes del archivo en el bucket, que no cuesta, o con SELECT value ... LIMIT 1 en la tabla, que lee toda la columna.

Costo estimado: COUNT(*): 0 bytes. Leer value en la tabla: 23.67 GB (≈22.05 GiB); entra en el primer TiB mensual gratuito, pero evita repetirlo sin necesidad.

-- BigQuery Studio
SELECT COUNT(*) AS tweets FROM tweets_bronze.entrada;

# Cloud Shell (sin costo de consulta)
gcloud storage cat -r 0-5000 gs://TU_BUCKET/war_tweets.txt | head -n 1

Salida esperada:

tweets
6798932

{"_type": "snscrape.modules.twitter.Tweet", "url": "https://twitter.com/skift/status/1508232397162258434", "date": "2022-03-27T23:59:59+00:00", "content": "Africa's Airline Recovery Faces Setback on Ukraine War's Higher Fuel Costs https://t.co/6aejPhMfU7", ... }

Comprueba: El conteo es 6798932 y la línea empieza con {"_type": "snscrape.modules.twitter.Tweet". En la tabla, el orden de las filas no está garantizado: SELECT ... LIMIT 1 puede devolver otro tweet.

Error frecuente y recuperación: Si COUNT(*) no da 6798932, la carga se interrumpió o se duplicó: repite el comando del paso 3 con --replace.

Paso 5 · Estimar costos antes de ejecutar · 12 min

Dónde: Cloud Shell.

Acción: Para cada consulta, predice cuántos bytes leerá y compruébalo con --dry_run (no ejecuta nada ni cuesta). Después ejecuta la cuarta con un tope de 200 MB: verás que BigQuery se niega y te dice cuánto necesitaba. La estimación de la cuarta promete 66.9 MB; la ejecución real exige 23.67 GB.

Costo estimado: Las estimaciones en seco no cuestan. La ejecución con tope se detiene antes de cobrar.

for SQL in \
 "SELECT COUNT(*) FROM tweets_bronze.entrada" \
 "SELECT value FROM tweets_bronze.entrada LIMIT 1" \
 "SELECT JSON_VALUE(value, '\$.id') FROM tweets_bronze.entrada" \
 "SELECT value FROM tweets_bronze.entrada TABLESAMPLE SYSTEM (0.1 PERCENT)"; do
  echo "$SQL"; bq query --nouse_legacy_sql --dry_run "$SQL"
done

bq query --nouse_legacy_sql --maximum_bytes_billed=200000000 \
 "SELECT value FROM tweets_bronze.entrada TABLESAMPLE SYSTEM (0.1 PERCENT)"

Salida esperada:

... will process 0 bytes of data.
... will process 23670340066 bytes of data.
... will process 23670340066 bytes of data.
... will process 66865367 bytes of data.

BigQuery error in query operation: ... Query exceeded limit for bytes billed: 200000000. 23670554624 or higher required.

Comprueba: Tres consultas piden 23,670,340,066 bytes (22.05 GiB) y COUNT(*) pide 0. La cuarta se estima en 66,865,367 pero la ejecución con tope falla exigiendo 23,670,554,624: la estimación no siempre se cumple.

Error frecuente y recuperación: Si el comando falla por las comillas del JSON_VALUE, escríbelo en una línea o en un archivo .sql y pásalo por stdin. Un SQL que empieza con -- pasado como argumento hace fallar a bq: usa stdin.

Paso 6 · De JSON a Parquet con Spark · 16 min

Dónde: Cloud Shell (editor de texto o cat > archivo) y consola de Dataproc para ver el lote.

Acción: Guarda el script json_a_parquet.py (lee el archivo como texto y lo guarda como Parquet), activa Dataproc y envía el trabajo como lote sin servidor. --deps-bucket es obligatorio; elige una región de Estados Unidos y usa la misma en todos tus lotes. El script cuenta las filas del Parquet que escribió: deben coincidir con tu Bronze.

Costo estimado: Dataproc Serverless cobra por los recursos que usa mientras corre. Un lote de Silver con hasta 4 ejecutores tardó unos 8 minutos en el ensayo; este script no se midió. Revisa el costo en Facturación y no dejes lotes repetidos.

gcloud services enable dataproc.googleapis.com
gcloud dataproc batches submit pyspark json_a_parquet.py \
  --region=us-central1 \
  --batch=json-a-parquet-001 \
  --deps-bucket=TU_BUCKET \
  --properties=spark.dynamicAllocation.maxExecutors=4

Salida esperada:

...
FILAS 6798932
Batch [json-a-parquet-001] finished.

Comprueba: La salida imprime FILAS 6798932, igual que COUNT(*) de tu Bronze, y gcloud storage ls gs://TU_BUCKET/tweets_parquet/ lista archivos .parquet.

Error frecuente y recuperación: Sin --deps-bucket, gcloud falla con "--deps-bucket was not specified" (se observó en el ensayo). Si el lote no arranca por red, la documentación de Dataproc Serverless exige Private Google Access en la subred (no se observó en el ensayo).

# json_a_parquet.py · lee el JSON Lines como texto y lo guarda como Parquet (una columna `value`).
from pyspark.sql import SparkSession

BUCKET = "gs://TU_BUCKET"
spark = SparkSession.builder.appName("json_a_parquet").getOrCreate()

crudo = spark.read.text(BUCKET + "/war_tweets.txt")           # transformación: cada línea queda en la columna `value`; aún no lee nada
crudo.write.mode("overwrite").parquet(BUCKET + "/tweets_parquet/")   # acción: aquí empieza el trabajo

resultado = spark.read.parquet(BUCKET + "/tweets_parquet/")
print("FILAS", resultado.count())                             # acción: cuenta las filas escritas

Entrega, costo y cierre

Qué conservar: la tabla tweets_bronze.entrada y el objeto war_tweets.txt; la sesión 4 parte de ellas. Anota tu manifiesto (nombre, tamaño, huella y filas).

Costo: el almacenamiento (22 GiB del archivo, 22 GiB de la tabla y unos 5.8 GiB del Parquet) se cobra por GiB y por mes; las consultas estimadas en seco no cuestan. Revisa Facturación después del lote de Spark.

Cierre de recursos: puedes borrar el Parquet que escribió Spark con gcloud storage rm -r gs://TU_BUCKET/tweets_parquet/ si no lo vas a usar. No borres tweets_bronze ni el archivo original.

Si falta un paso anterior, repítelo antes de seguir: cada comprobación depende de la anterior.
