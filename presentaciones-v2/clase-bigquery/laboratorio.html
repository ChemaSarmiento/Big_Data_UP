Laboratorio · all_data.csv en BigQuery

Laboratorio ejecutivo · 80 minutos. Tres etapas y tres archivos SQL. En cada paso: abrir, copiar y ejecutar una consulta.

Antes de empezar

El docente prepara emergent_bronze, emergent_silver y emergent_gold en el proyecto de práctica. Así el grupo empieza mirando Bronze. Para cargar durante clase, sube all_data_muestra.csv como CSV en emergent_bronze.entrada, con las 15 columnas STRING de esquema-bronze.json. Se observaron 4500 filas en esta muestra de trabajo.

En Google Cloud: BigQuery → SQL workspace → Nueva consulta. Copia el bloque numerado y pulsa Ejecutar. El docente prepara el proyecto, permisos y facturación. No hace falta configurar la cuenta durante el laboratorio.

El archivo original pesa más de 20 GB. El docente lo prepara previamente en GCS; el grupo usa esta observación.

Paso 1 · Bronze · ver lo que llegó · 20 min

Abre BigQuery Studio → SQL workspace → Nueva consulta. Carga all_data_muestra.csv en emergente_bronze.entrada con el esquema incluido: 15 columnas STRING, formato CSV y una fila de cabecera. Ejecuta estas consultas. Compara el valor original TLALPAN con municipio_limpio. Bronze conserva la entrada; todavía no corrige sus valores.

Comprueba: 4500 filas observadas. municipio conserva espacios finales y fechaRegistro mantiene fecha y hora.

Si no coincide: Revisa delimitador coma, UTF-8, cabecera y comillas. No uses autodetección: las columnas crudas se guardan como STRING.

10_bronze.sql ↓

Ver consultas
-- Bronze muestra los valores como llegaron desde el CSV.
-- Carga previa: all_data_muestra.csv en emergente_bronze.entrada.
SELECT producto, presentacion, marca, precio, fechaRegistro, municipio
FROM emergente_bronze.entrada
WHERE producto='REFRESCO' AND marca='SPRITE' AND municipio LIKE 'TLALPAN%'
LIMIT 10;

-- La limpieza se muestra como una consulta; la tabla original no cambia.
SELECT municipio AS municipio_original, TRIM(municipio) AS municipio_limpio,
 precio AS precio_original, SAFE_CAST(precio AS NUMERIC) AS precio_numerico
FROM emergente_bronze.entrada
WHERE producto='REFRESCO' AND marca='SPRITE' AND TRIM(municipio)='TLALPAN'
LIMIT 5;

SELECT COUNT(*) AS filas_bronze FROM emergente_bronze.entrada;
-- Esperado con la muestra: 4500.

Paso 2 · Silver · limpiar, tipar y revisar qué se pierde · 30 min

Abre otra consulta y ejecuta los siete bloques numerados en orden. 1: crea una tabla limpia (incluye direccion, no solo el nombre comercial). 2: guarda aparte los registros que no se pueden usar. 3: compara conteos. 4: busca filas que, ya limpias, quedaran idénticas en todos sus campos — TRIM y SAFE_CAST no detectan eso, solo agrupar sí. 5: desglosa POR QUÉ se rechazó cada fila, no solo cuántas. 6: confirma el periodo real de fechas. 7: compara precios por categoría, para no marcar como sospechoso un precio alto que es real en su categoría (televisores, lavadoras).

Comprueba: 4500 filas observadas y aceptadas; 0 para revisar; 0 filas idénticas repetidas (bloque 4); periodo observado 2011-01-10 a 2015-12-09 (bloque 6); precios hasta 13497 son electrodomésticos reales, no error (bloque 7).

Si no coincide: Si SAFE_CAST devuelve NULL, busca la fila rechazada y lee el motivo en el bloque 5. Conserva la regla; revisa el valor original en Bronze. Si el bloque 4 no queda vacío, antes de seguir decide si esas filas son un error de carga o observaciones legítimas repetidas.

20_silver.sql ↓

Ver consultas
-- 1. Crear Silver con nombres limpios y tipos útiles. Bronze queda intacta.
-- direccion se conserva: sin ella, dos tiendas distintas con el mismo
-- nombre comercial en el mismo municipio se verían como una sola en Gold.
CREATE OR REPLACE TABLE emergente_silver.precios_limpios AS
SELECT TRIM(producto) AS producto, TRIM(presentacion) AS presentacion,
 TRIM(marca) AS marca, TRIM(categoria) AS categoria,
 SAFE_CAST(precio AS NUMERIC) AS precio_mxn,
 SAFE_CAST(fechaRegistro AS DATE) AS fecha,
 TRIM(cadenaComercial) AS cadena_comercial,
 TRIM(nombreComercial) AS establecimiento,
 TRIM(direccion) AS direccion,
 TRIM(estado) AS estado, TRIM(municipio) AS municipio,
 SAFE_CAST(latitud AS FLOAT64) AS latitud,
 SAFE_CAST(longitud AS FLOAT64) AS longitud
FROM emergente_bronze.entrada;

-- 2. Separar los registros que requieren revisión.
CREATE OR REPLACE TABLE emergente_silver.precios_para_revisar AS
SELECT * FROM emergente_silver.precios_limpios
WHERE producto IS NULL OR marca IS NULL OR presentacion IS NULL
 OR precio_mxn IS NULL OR precio_mxn<=0 OR fecha IS NULL;

-- 3. Revisar el conteo. En lo observado: 4500 en Silver y 0 para revisar.
SELECT (SELECT COUNT(*) FROM emergente_bronze.entrada) AS bronze,
 (SELECT COUNT(*) FROM emergente_silver.precios_limpios) AS silver,
 (SELECT COUNT(*) FROM emergente_silver.precios_para_revisar) AS revisar;

-- 4. Qué podríamos revisar: filas que, ya limpias, quedan idénticas en
-- todos sus campos. TRIM/SAFE_CAST no las detecta -- solo agrupar sí.
-- Si aparecieran, un conteo posterior (por ejemplo, Gold) se duplicaría
-- sin que nada lo avise.
SELECT producto, marca, presentacion, precio_mxn, fecha, establecimiento,
 direccion, COUNT(*) AS veces_repetida
FROM emergente_silver.precios_limpios
GROUP BY producto, marca, presentacion, precio_mxn, fecha, establecimiento, direccion
HAVING COUNT(*) > 1;
-- Vacío en lo observado: no encontramos filas idénticas repetidas aquí.

-- 5. Qué podríamos revisar: POR QUÉ se rechazó cada fila, no solo cuántas.
-- Un solo conteo (bloque 3) no distingue si el problema es el precio, la
-- fecha o un campo de texto vacío -- este desglose sí.
SELECT
 COUNTIF(producto IS NULL) AS sin_producto,
 COUNTIF(marca IS NULL) AS sin_marca,
 COUNTIF(presentacion IS NULL) AS sin_presentacion,
 COUNTIF(precio_mxn IS NULL) AS precio_no_convertible,
 COUNTIF(precio_mxn IS NOT NULL AND precio_mxn<=0) AS precio_no_positivo,
 COUNTIF(fecha IS NULL) AS fecha_no_convertible
FROM emergente_silver.precios_limpios;
-- En lo observado: todo en cero. Si algo sube, aquí está el motivo exacto,
-- no solo el total.

-- 6. Qué podríamos revisar: ¿el periodo que creemos tener es el que
-- de verdad hay? Bronze no lo dice; aquí sí se puede comprobar.
SELECT MIN(fecha) AS fecha_minima, MAX(fecha) AS fecha_maxima
FROM emergente_silver.precios_limpios;
-- En lo observado: 2011-01-10 a 2015-12-09 -- tres años sin continuidad,
-- no una serie diaria completa. No asumas cobertura entre esas fechas.

-- 7. Qué podríamos revisar: ¿un precio aceptado es creíble para ESE
-- producto, no solo distinto de cero? all_data mezcla categorías de
-- precio muy distinto (refrescos vs. televisores) -- un límite fijo
-- sin categoría marca como "sospechoso" algo que es real.
SELECT categoria, MIN(precio_mxn) AS precio_minimo, MAX(precio_mxn) AS precio_maximo,
 COUNT(*) AS filas
FROM emergente_silver.precios_limpios
GROUP BY categoria
ORDER BY precio_maximo DESC
LIMIT 5;
-- En lo observado: los precios más altos (hasta 13497) son televisores,
-- lavadoras y refrigeradores reales -- no errores de captura. Un filtro
-- "precio > 10000" sin categoría los marcaría como sospechosos por error.

Paso 3 · Gold · preparar una comparación sin perder el conflicto de vista · 30 min

Abre otra consulta y ejecuta los cuatro bloques. 1: Gold agrupa el precio por producto, marca, presentación, dirección, fecha y tienda — la dirección entra al grano para no fusionar dos tiendas distintas que comparten el mismo nombre comercial. 2: muestra el caso Sprite del 19 de marzo de 2014 en Tlalpan, con una columna estado_precio: dice "conflicto" solo si había más de un precio distinto en el mismo grupo; MIN() por sí solo no avisa, solo elige el menor en silencio. 3: escanea conflictos en TODA la muestra observada, no solo en el caso armado. 4: comprueba que el agregado no perdió ni duplicó filas de Silver.

Comprueba: Dos establecimientos observados (direcciones distintas): 15.10 y 15.50 MXN, ambos marcados único. En toda la muestra (bloque 3): 0 de 4500 grupos en conflicto. Integridad (bloque 4): 2 observaciones en Gold, 2 filas en Silver — coinciden.

Si no coincide: Si no aparecen dos filas, revisa fecha, producto, marca, presentación y municipio. Si el bloque 3 muestra grupos en conflicto, antes de usar el precio menor revisa si son en verdad la misma tienda. Si el bloque 4 no coincide, el GROUP BY perdió o duplicó algo — no lo ignores.

30_gold.sql ↓

Ver consultas
-- 1. Gold: precio por tienda para un producto, presentación y fecha.
-- direccion entra al grano: dos tiendas con el mismo nombre comercial en
-- el mismo municipio no se mezclan en una sola fila.
-- estado_precio queda lista para cuando SÍ haya más de un precio en el
-- mismo grupo -- MIN() por sí solo elige el menor en silencio y no avisa.
CREATE OR REPLACE TABLE emergente_gold.precio_sprite_tlalpan AS
SELECT fecha, estado, municipio, producto, marca, presentacion,
 cadena_comercial, establecimiento, direccion, MIN(precio_mxn) AS precio_mxn,
 COUNT(*) AS observaciones,
 CASE WHEN COUNT(*) > 1 AND MIN(precio_mxn) <> MAX(precio_mxn)
      THEN 'conflicto' ELSE 'único' END AS estado_precio
FROM emergente_silver.precios_limpios
WHERE fecha=DATE '2014-03-19' AND producto='REFRESCO' AND marca='SPRITE'
 AND presentacion='BOTELLA 2 LT. NO RETORNABLE'
 AND estado='DISTRITO FEDERAL' AND municipio='TLALPAN'
GROUP BY fecha, estado, municipio, producto, marca, presentacion,
 cadena_comercial, establecimiento, direccion;

-- 2. Observado: dos tiendas (direcciones distintas), cada una con un solo
-- precio -- ambas 'único'. 15.10 y 15.50 MXN.
SELECT establecimiento, direccion, precio_mxn, observaciones, estado_precio
FROM emergente_gold.precio_sprite_tlalpan ORDER BY precio_mxn;
-- Evidencia histórica. No prueba existencia ni precio actual.

-- 3. Qué podríamos revisar: ¿cuántos conflictos hay en TODA la muestra
-- observada, no solo en el caso de Sprite/Tlalpan que armamos arriba?
SELECT
 COUNTIF(precios_distintos > 1) AS grupos_en_conflicto,
 COUNT(*) AS grupos_totales
FROM (
 SELECT producto, marca, presentacion, fecha, estado, municipio,
  cadena_comercial, establecimiento, direccion,
  COUNT(DISTINCT precio_mxn) AS precios_distintos
 FROM emergente_silver.precios_limpios
 GROUP BY producto, marca, presentacion, fecha, estado, municipio,
  cadena_comercial, establecimiento, direccion
);
-- En lo observado: 0 de 4500 grupos en conflicto. No asumas que el
-- archivo completo se comporta igual -- aquí sí vale la pena repetir
-- esta consulta cuando se cargue.

-- 4. Qué podríamos revisar: ¿el agregado perdió o duplicó filas al
-- agrupar? El total de observaciones en Gold debe ser igual al número
-- de filas de Silver que de verdad cumplen el mismo filtro.
SELECT
 (SELECT SUM(observaciones) FROM emergente_gold.precio_sprite_tlalpan) AS suma_en_gold,
 (SELECT COUNT(*) FROM emergente_silver.precios_limpios
  WHERE fecha=DATE '2014-03-19' AND producto='REFRESCO' AND marca='SPRITE'
   AND presentacion='BOTELLA 2 LT. NO RETORNABLE'
   AND estado='DISTRITO FEDERAL' AND municipio='TLALPAN') AS filas_en_silver;
-- Deben coincidir (2 y 2). Si no coinciden, el GROUP BY perdió o
-- duplicó algo -- no lo asumas, compáralo cada vez.

Ruta docente para el archivo completo

Conservar el original en un bucket autorizado, con nombre de objeto, tamaño, generación/checksum y manifiesto. Cargar desde GCS directamente a emergente_bronze.entrada con el mismo esquema de 15 columnas STRING — no transferir 20.7 GB a un disco local ni a Cloud Shell. Antes de correr 20_silver.sql y 30_gold.sql sobre el archivo completo, repetir el bloque 4 de Silver (filas idénticas repetidas) y revisar cuántos grupos de Gold quedan con estado_precio = conflicto: en la muestra observada ninguno lo tuvo, y eso no prueba que el archivo completo se comporte igual. Ejecutar una vez, guardar controles y usar tablas preparadas en clase. El diseño no presupone que lo observado en la muestra valide todas las filas del archivo.

Para optimizar: selecciona las columnas necesarias, filtra por fecha y revisa el estimado de bytes antes de ejecutar. LIMIT limita las filas de salida; no necesariamente los datos leídos. Con el archivo completo, el docente ensaya y comparte los resultados.
